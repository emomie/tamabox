# Plan 08-06 — EDGE-05: Block confirm modal element + JS dialog control

## Goal

Replace the direct Block POST form (currently inline in `templates/Users/dashboard.php` HIT branch) with a `<dialog>`-based bottom-sheet confirm modal. ## Risks

- CakePHP `Form->create()` injects CSRF token. The `<dialog>` content is server-rendered (not lazy-loaded), so the token is present at page load. No need for JS to fetch a fresh token.
- Multiple HIT messages → multiple `<dialog>` elements. Unique IDs via `$msg->id` UUID prevent collision. JS uses `getElementById(triggerData)` which returns the specific dialog.
- `<dialog>::backdrop` rendering: native `<dialog>` shows its backdrop only via `showModal()`, not `show()`. JS uses `showModal()` exclusively (UI-SPEC).
- `mb_substr($senderHandle, 0, mb_strpos($senderHandle, '.') ?: mb_strlen($senderHandle))` — if `mb_strpos` returns 0 (handle starts with a `.`, unlikely), the `?:` truth-test treats 0 as false and falls through to `mb_strlen`. Acceptable: handles never start with `.` per Bluesky DID format.
- The existing inline Block form is also asserted in `BlocksControllerTest.php` indirectly. Verify by grep: tests assert on POST → response, not on dashboard markup. Safe.

## Out of scope

- ESC-to-cancel keyboard binding (native `<dialog>` provides this automatically — no JS needed)

- Animating the sheet slide-up (hi-fi implies it; `<dialog>` doesn't natively animate; deferred to v3 with `@starting-style` polyfill consideration)
